# Локальные и облачные модели

**Статус:** план. Конкретный runtime и модели для собственного ЦОД выбираются после инвентаризации GPU/CPU, RAM, VRAM, сети и целевой нагрузки. Yandex Cloud рассматривается как возможный облачный backend; конкретная услуга и разрешённый сценарий использования TBD.

## 1. Цель

Поднять inference как backend платформы, не связывая клиентский API-контракт с конкретным runtime или облаком. Возможны два типа размещения: собственная модель в ЦОД и модель/вычислительный ресурс, доступный через Yandex Cloud. Во втором случае обработка происходит в облачной инфраструктуре, а не на собственном оборудовании. Качество, права использования, регион обработки, стоимость, производительность и условия проксирования проверяются отдельно.

## 2. Схема

```text
Internet/client
  → HTTPS reverse proxy / API ingress
  → platform auth + rate limits
  → router
  → local adapter (внутренняя сеть)
  → inference server (GPU/CPU worker)
  → model artifact + tokenizer
```

Собственный inference server не публикуется наружу. Только адаптер имеет сетевой доступ к нему. Для Yandex Cloud адаптер обращается к выбранному облачному endpoint из server-side окружения; credentials никогда не попадают браузеру или клиенту. Control plane и inference plane разделены firewall/ACL; админ-доступ к инфраструктуре — через контролируемую административную сеть. Политику отправки данных в облако задавать явно на уровне модели/workspace.

## 3. Yandex Cloud как стартовый/резервный backend

Сначала уточнить, какой именно сценарий имеется в виду:

1. **Управляемый API модели:** платформа вызывает облачный endpoint модели. Это отдельный adapter с credentials, лимитами и тарификацией сервиса.
2. **Вычислительные ресурсы:** команда разворачивает выбранную открытую модель и runtime на виртуальных/выделенных ресурсах облака. Тогда жизненный цикл артефакта и runtime остаётся ответственностью команды.

Не называть облачные модели «локальными в нашем ЦОД»: это другой домен обработки и иной набор договорных/сетевых зависимостей. До выбора сравнить оба варианта с собственным inference по критериям: разрешён ли multi-tenant proxy/resale; доступные модели и лицензии; регион/поток данных; SLA и лимиты; фактическая цена на целевой нагрузке; latency и квоты; логи и retention; экспорт/удаление данных; credential rotation; процедура отключения и fallback. Конкретные свойства Yandex Cloud не считаются подтверждёнными, пока не проверены по актуальным условиям выбранной услуги.

Облачный adapter должен пройти те же contract tests и capability matrix, что и локальный. Не отправлять облачному backend проекты/запросы, для которых политика workspace запрещает облачную обработку.

## 4. Выбор runtime — не фиксировать без замеров

Рассмотреть кандидатов по hardware и требованиям:

- **vLLM** — вариант для GPU serving и конкурентной нагрузки, если модель и оборудование поддерживаются;
- **llama.cpp** — полезен для квантованных моделей, CPU/GPU смешанного исполнения и компактных стендов;
- **Ollama** — удобен для быстрого локального прототипирования; для продуктивного многопользовательского serving отдельно оценить наблюдаемость, concurrency и эксплуатационные требования.

Это не окончательная рекомендация: сначала PoC на реальном оборудовании. Совместимые HTTP endpoints разных runtimes не гарантируют одинаковое поведение, поэтому нужен собственный adapter/contract test.

## 5. Манифест модели

Для каждого артефакта хранить версионируемую запись:

- внутренний ID, отображаемое имя и публичный API `model`;
- источник, revision/commit, checksum, дата загрузки;
- tokenizer и chat template версия;
- формат/квантование, размер контекста;
- runtime и версия, параметры запуска;
- лицензия/разрешённые сценарии и ссылка на проверку;
- hardware requirement, concurrency profile, измерения latency/throughput;
- доступные capabilities: streaming, tools, JSON mode — только подтверждённые тестом;
- status: staged, canary, active, degraded, disabled, retired.

Не загружать неизвестные веса в production без проверки происхождения, checksum, лицензии и безопасности артефактов.

## 6. Жизненный цикл

1. **Select:** выбрать candidate по задаче и аппаратным требованиям; проверить лицензию и происхождение.
2. **Acquire:** скачать по контролируемому процессу в staging; проверить checksum и размер; не скачивать runtime-артефакты произвольно из production worker.
3. **Validate:** запуск smoke tests, tokenizer/template tests, функциональные тесты и проверка prompt injection/unsafe output на уровне приложения.
4. **Benchmark:** прогнать целевые нагрузки, замерить TTFT, tokens/sec, p95, VRAM, cold start, throughput и error rate. Тестировать concurrent запросы и длинный контекст.
5. **Stage:** развернуть без клиентского трафика; проверить health, readiness, warmup.
6. **Canary:** ограничить долю/пилотную группу, следить за метриками и ручной обратной связью.
7. **Promote/Rollback:** явное одобрение, версия конфигурации, возможность вернуть предыдущий артефакт.
8. **Retire:** запрет нового трафика, завершение активных запросов, отзыв маршрута и документированное удаление артефакта по политике.

## 7. Проверки перед активацией

- `/health` и `/ready` доступны только внутренне.
- Простая генерация, Unicode/русский текст, пустой/длинный вход, stream завершение.
- Ограничение `max_tokens`, контекста, размера payload и параллельности.
- Отмена клиента, timeout, worker restart, отсутствие GPU memory.
- Формат ошибок нормализуется адаптером.
- Usage: точные токены от runtime или явно помеченная оценка; не выдавать оценку за точные данные.
- Нагрузка не вытесняет control plane; действует backpressure и очередь с ограничением.
- Smoke test и benchmark связаны с model artifact revision.

## 8. Операционная безопасность

- Egress inference worker ограничен необходимыми адресами; по умолчанию runtime не скачивает произвольные файлы и не имеет свободного доступа в интернет.
- Контейнеры без root, минимальные capabilities, read-only model mount где возможно, ограничения CPU/RAM/GPU и файловой системы.
- Разделить доверенные конфигурации запуска и пользовательский prompt; не запускать код, сгенерированный моделью.
- Метрики GPU/VRAM, queue depth, OOM, batch size, TTFT, tokens/sec, restart и температуры/состояния оборудования при доступности.
- Не включать prompt/response в логи runtime по умолчанию; проверить стороннюю телеметрию/обновления.

## 9. Модели и публикация

Публичный model ID стабилен только если команда гарантирует семантику. Версионированные ID или объявления смены версии предпочтительнее скрытой замены поведения. При отключении модели API должен возвращать документированную ошибку, а не молча подменять её другой моделью.

## 10. Неизвестные параметры

Инвентаризировать: GPU модель/количество/VRAM, CPU, RAM, storage и скорость чтения артефактов, сеть, ОС/виртуализация, доступность охлаждения/питания и резервирования, требуемые concurrency, целевые latency и класс моделей.
