# Техническая архитектура платформы

**Статус:** логическая схема; технология, масштаб и deployment topology TBD после инвентаризации ЦОД.

## 1. Логические зоны

1. **Web frontend** — публичный сайт, кабинет пользователя, админ-панель. Браузер обращается только к платформенному backend по HTTPS.
2. **Identity/control plane** — пользователи, сессии, организации, проекты, роли, ключи, политики и каталог моделей.
3. **API ingress** — OpenAI-совместимые endpoints; аутентификация ключа, rate limit, валидация и correlation ID.
4. **Router** — проверка доступности и capability, применение явного правила маршрутизации, вызов адаптера.
5. **Adapters** — отдельная реализация на каждую локальную или внешнюю систему inference; нормализация формата и ошибок. Yandex Cloud — отдельный adapter/backend, если выбранный сервис и договор разрешают этот сценарий.
6. **Inference plane** — локальные inference servers в собственном ЦОД и/или облачные inference endpoints/вычислительные ресурсы. Для каждого маршрута задаются границы обработки данных, доступность, цена и разрешённые workspace.
7. **Metering/ledger** — события использования и денежные начисления с версией тарифа, без потери событий.
8. **Operations** — метрики, логи, трассировки, аудит, алерты, deployment/rollback.

## 2. Поток запроса

1. Клиент посылает HTTPS-запрос с `Authorization: Bearer <platform_key>`.
2. Ingress проверяет TLS, формат, размер, частоту и статус ключа; находит workspace/project и ограничения.
3. Router проверяет публичный `model`, активность модели и поддержку параметров. Никогда не выбирает более дорогую/неэквивалентную модель скрыто.
4. Adapter преобразует платформенный нормализованный request в формат backend; передаёт upstream secret только сервер-сервер.
5. Ответ нормализуется; streaming транслируется с корректным завершением/ошибкой.
6. Metering пишет событие с request ID, фактическим route/model, usage source, latency и тарифной версией. Prompt/response не пишутся в обычные логи.
7. Клиент получает совместимый ответ и безопасный request ID для диагностики.

При частичном сбое/отмене надо различать: запрос не дошёл, backend начал работу, ответ частичный, usage неизвестен. Денежное списание и повторная отправка не должны создавать двойное начисление.

## 3. Разделение control plane и inference plane

Control plane содержит учётные данные и конфигурацию, но не должен становиться узким местом генерации. Inference plane не получает доступ к полным пользовательским аккаунтам. Между зонами — аутентифицированный внутренний канал, минимальные права, allowlist сетевых соединений.

Локальный inference endpoint по умолчанию недоступен из пользовательской сети и интернета. Вызов только через адаптер/внутреннюю сеть. Для облачного backend используются отдельные server-side credentials и сетевые политики; ключи не попадают клиенту. При маршрутизации в облако до отправки запроса применяются утверждённые правила данных и региона обработки. Административные endpoints не смешивать с публичным API.

## 4. Ключевые доменные сущности

- `User`: login/email, hash пароля, verification state, status.
- `Session`: идентификатор/хэш refresh token, сроки, device metadata, revoke state.
- `Workspace`: личный или юридического лица, состояние и политика.
- `Membership`: user, workspace, role.
- `Project`: workspace, название, лимиты.
- `ApiKey`: hash, короткий видимый prefix, project, scope, quotas, created/revoked/last_used.
- `Model`: публичный ID, capability, status, pricing version, route reference.
- `ProviderAdapter`: тип, endpoint reference, health/config version; секреты в secret manager, не БД приложения.
- `UsageEvent`: request ID, tenant/project, model, route, token counts/source, duration, status, tariff version, amount/estimate.
- `LedgerEntry`: неизменяемая денежная запись и ссылка на usage/корректировку.
- `AuditEvent`: actor, action, target, reason, timestamp, correlation ID.
- `Incident`: сервис, impact, timeline, status, resolution.

## 5. Маршрутизация и отказоустойчивость

- Сначала явная маршрутизация по выбранному публичному ID → конкретная модель/backend.
- Fallback включается только для заранее определённых ошибок, capability и эквивалентной политики. Публичная модель/фактический backend фиксируются в usage.
- Не повторять автоматически потенциально небезопасный запрос после начала генерации, если повтор создаёт дубль/начисление.
- Circuit breaker/health checks и отключение модели должны иметь ручной контролируемый override.
- Идемпотентность и семантика `Idempotency-Key` — определить до публичного контракта.

## 6. Хранение и логи

Данные разделить по классу: идентификация, секреты, эксплуатационные метаданные, usage/биллинг, содержимое запросов. Для каждого задать доступ, шифрование, цель и срок хранения. По умолчанию хранить только метаданные, нужные для работы и биллинга; сырые prompts/responses не собирать без явного продуктового решения и юридической проверки.

## 7. Масштабирование и capacity

Планирование ресурсов основывать на измерениях: модель/квантование, размер контекста, concurrency, TTFT, токены/с, GPU memory, очередь и доля streaming запросов. Лимитировать concurrency и длину входа до исчерпания GPU. Подробности локального сервинга — LOCAL_MODELS.md.
