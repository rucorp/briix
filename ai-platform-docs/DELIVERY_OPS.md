# План поставки, приёмка и эксплуатация

**Статус:** рабочий план; сроки зависят от команды, стека и инвентаризации ЦОД.

## Этап 0 — аудит имеющегося и решения

- Инвентаризация существующего шлюза, локальных моделей, адаптеров, тестов, metering, лимитов, наблюдаемости и deployment.
- Не переписывать существующий шлюз до аудита: определить, что можно повторно использовать, а что требует доработки.
- Инвентаризация серверов, GPU/VRAM, сети, storage, ОС и резервирования.
- Уточнить сегмент первых клиентов и API-only vs chat пользователя.
- Сравнить собственный ЦОД, Yandex Cloud managed inference и Yandex Cloud compute на одинаковом профиле нагрузки по COST_MODEL.md.
- Проверить права/условия на локальные веса и будущих внешних поставщиков.
- Утвердить auth, data retention, тарифную модель и финансово-договорный процесс.
- Зафиксировать домен, стек, deployment и владельцев эксплуатации.

**Выход:** закрыты блокирующие TBD, спецификация MVP и capacity PoC.

## Этап 1 — доведение существующей платформы до закрытой альфы

- Повторно использовать существующий шлюз и локальные модели после аудита; сначала закрыть критичные gaps, не переписывать работающие компоненты без причины.
- Публичный лендинг и документация.
- Регистрация/вход, workspace/project, роли, API-ключи.
- Mock adapter, OpenAI-compatible API и contract tests.
- Один inference backend через adapter: локальный endpoint в ЦОД или выбранный облачный backend; второй вариант может быть подключён позже.
- Usage/лимиты, базовая админка, audit, метрики и алерты.

**Выход:** команда может создать пользователя, выполнить запрос и безопасно диагностировать его.

## Этап 2 — закрытая альфа

- Ограниченный список приглашённых разработчиков/юрлиц.
- Квоты и ручной финансовый процесс, если согласован; без публичного обещания SLA.
- Наблюдение за latency, ошибками, cost/usage accuracy, поддержкой и UX.
- Тест восстановления из backup, отзыв ключей и incident drill.

**Gate:** нет межклиентской утечки; критичные сценарии API пройдены; нагрузка не истощает ресурсы; понятен unit economics по локальной модели.

## Этап 3 — внешний adapter

Для каждого поставщика отдельно: договорное разрешение и региональные ограничения, credential rotation, capability matrix, ошибки/лимиты, цена и usage reconciliation, тест деградации и процедура отключения. Новый backend проходит staging → canary → activation с rollback.

## Этап 4 — чат и рост

- Web chat как дополнительный UI к тому же gateway.
- Отдельная free quota и антиабьюз; условия free-tier источников письменно проверены.
- Измерить переход из чата в API и платный сегмент; free traffic не должен вытеснять платных клиентов.

## Критерии релизной готовности

- Все важные пользовательские сценарии имеют e2e/acceptance tests.
- Проверены tenant isolation, access control, ключи и админ-аудит.
- OpenAPI соответствует реально реализованному контракту.
- Есть dashboard и alerts для gateway, router, inference, storage и GPU.
- Проведены нагрузочный тест и отказ одного inference worker.
- Проверены backup restore, deploy rollback, key revoke и incident response.
- Есть правила хранения/удаления данных и опубликованы фактические Terms/Privacy.
- Цены, статусы «оценочно/фактически», документы и лимиты согласованы с реализацией.
- Контакт поддержки и статус-страница работают.

## Эксплуатационные runbooks

Минимум: модель недоступна; GPU OOM; перегрузка/очередь; всплеск 429/5xx; повреждённый артефакт; утечка API-ключа; сбой биллинга/метеринга; утечка tenant boundary; восстановление БД/backup; аварийный rollback модели.

Для каждого: сигнал обнаружения, ответственный, безопасное действие, коммуникация клиенту, восстановление, сверка usage/денег, post-incident review.
