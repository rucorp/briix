# Сравнение полной стоимости: свой ЦОД и Yandex Cloud

**Статус:** шаблон расчёта, ценовые данные не заполнены. Условия и цены Yandex Cloud нужно взять из актуального коммерческого предложения/калькулятора на дату расчёта. Не сравнивать номинальную цену токена с «бесплатным» собственным железом.

## 1. Цель сравнения

Выбрать самый дешёвый **достаточно надёжный и функционально сопоставимый** вариант для стартовой нагрузки. Считать как минимум три сценария:

A. Собственный ЦОД: уже имеющийся gateway + локальная модель.
B. Yandex Cloud managed inference: вызов готового API модели.
C. Yandex Cloud compute: аренда ресурсов и самостоятельный запуск модели (если этот вариант рассматривается).

Считать отдельно:

- **денежный отток ближайших месяцев** — важно для старта и runway;
- **полную экономическую стоимость (TCO)** — нужна для долгосрочного решения;
- **предельную стоимость дополнительной нагрузки** — чтобы понять, куда маршрутизировать следующий запрос.

Не принимать решение только по средней цене токена: модели, качество, latency, контекст, concurrency и ограничения должны быть сопоставимы.

## 3. Формулы

### A. Собственный ЦОД — полная стоимость за месяц

`C_DC_full = C_hardware_amortization + C_power_and_cooling + C_rack/network + C_maintenance + C_ops + C_storage_and_backup + C_HA/reserve + C_other`

Разложить:

- амортизация/стоимость капитала GPU-серверов на выбранный срок;
- электричество сервера × фактическая нагрузка × тариф; охлаждение/PUE учитывать отдельно или в составе facility charge, не дважды;
- стойка, сеть, диски и резервное копирование;
- ремонт, запасные компоненты и замена оборудования;
- доля инженерного времени на обновления, мониторинг, инциденты и безопасность;
- резервирование/неиспользуемая мощность для пиковой нагрузки и отказов.

Для решения «что делать сейчас» дополнительно считать `C_DC_incremental`: реальные дополнительные расходы от обслуживания нового трафика и цена дефицита GPU-capacity. Уже купленное оборудование не означает нулевую полную стоимость, но его историческую цену нельзя второй раз считать как новый денежный расход.

### B. Yandex Cloud managed inference

`C_YC_managed = Σ(input_tokens_model × input_rate + output_tokens_model × output_rate) + request/minimum charges + network/storage/logs + support/other fees`

Уточнить тарифные единицы, округление, минимальное списание, бесплатные квоты, ограничения, регион и валюту. Не включать в финмодель бесплатные квоты, если они временные, персональные или не разрешают production/посредническое использование.

### C. Yandex Cloud на собственной модели

`C_YC_compute = Σ(instance_hours × hourly_rate) + disks/snapshots + network/egress + load balancer + storage/logging + support/other fees`

Добавить резерв на постоянно включённые GPU, если сервис требует прогрева/низкой задержки. Для scale-to-zero учесть cold start, ограничение доступности и стоимость прогрева.

## 4. Стартовая наценка

Рабочая гипотеза команды: наценка не выше 20% к cost basis, пока не получены специальные условия от поставщиков. При ровно 20% markup: `client_price = cost_basis × 1.20`; это соответствует 16.7% валовой марже от цены до прочих расходов, а не 20% марже.

Сначала определить cost basis для каждого backend. Для внешнего тарифа это не всегда только цена поставщика: могут быть комиссии оплаты, валютная конвертация, стоимость платформенной инфраструктуры и потери на повторах/ошибках. Для локальной модели cost basis требует отдельного метода распределения затрат на вычисление. Не добавлять расходы дважды и явно зафиксировать, что включено в тариф. После получения скидки/квоты/других привилегий пересчитать cost basis и экономику до изменения клиентского тарифа.

## 5. Стоимость единицы и порог безубыточности

Для одинакового тестового профиля посчитать:

- стоимость 1 000 запросов и 1 млн входных/выходных токенов;
- стоимость при низкой, базовой и пиковой нагрузке;
- максимальную обработанную нагрузку до деградации;
- стоимость при target latency и при требовании резерва.

В упрощённом виде для сравнения fixed + variable:

`C_DC = F_DC + v_DC × Q`

`C_cloud = F_cloud + v_cloud × Q`

где `Q` — одинаковый объём сопоставимой работы; break-even при равных тарифных предпосылках: `Q* = (F_DC - F_cloud) / (v_cloud - v_DC)`, только если знаменатель и знак дают экономически осмысленное значение. Для managed API цены могут зависеть отдельно от input/output и модели, поэтому точнее считать таблицей сценариев, а не одной ставкой.

## 7. Практический метод проверки

1. Зафиксировать один и тот же синтетический/разрешённый тестовый набор запросов и acceptance критерии качества.
2. Замерить local gateway → локальная модель: token counts, latency, throughput, GPU utilization, power, errors.
3. На том же профиле проверить YC-варианты; отдельно пометить тарифы, которые пока оценочные.
4. Рассчитать низкий/базовый/пиковый сценарий и полный, предельный, денежный отток.
5. Проверить условия платформенного доступа: multi-tenant, proxy/resale, ограничения пользователей, обработка и хранение данных, rate limits, SLA.
6. Провести ограниченный пилот, собрать фактическую нагрузку и пересчитать модель.
7. Выбрать: один backend, primary + fallback или per-model routing. Не переключать трафик только по цене, если качество/данные/доступность не эквивалентны.
