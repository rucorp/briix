# Аутентификация, авторизация и безопасность

**Статус:** рекомендуемая базовая политика. Перед production проверить реализацию тестированием безопасности и юридически согласовать обработку данных.

## 1. Решение по входу

Рекомендуемый первый вариант: **email + пароль, без входа через Google/Apple/соцсети**. Email используется для подтверждения аккаунта и восстановления. Это не требует внешнего OAuth-провайдера, но всё же требует доступного канала почты.

Если принципиально не привязываться к email/телефону, потребуется отдельная политика восстановления: invite-only аккаунты, резервные коды и/или ручная проверка администратором. Потеря единственного пароля иначе означает потерю доступа. Это отдельное решение, не скрытая настройка.

**PIN на экранном keypad не рекомендуется как первичная аутентификация веб-сервиса:** короткий PIN имеет низкую энтропию, подвержен наблюдению и автоматическому перебору. PIN может быть только локальным вторичным unlock после полноценной аутентификации, с лимитом попыток и без восстановления аккаунта.

В дальнейшем рассмотреть WebAuthn/passkeys и/или TOTP MFA; для платформенных администраторов MFA обязательна до публичного запуска.

## 2. Пароли и сессии

- Не хранить пароль в открытом виде и не шифровать обратимым способом; применять современный password hashing (например, Argon2id с проверенными параметрами реализации).
- Проверять минимальную длину и скомпрометированные/часто используемые пароли; не навязывать бессмысленную регулярную смену по календарю.
- Rate limit и progressive delays на login/reset; защита от credential stuffing, одинаковый нейтральный ответ для неизвестного логина.
- HTTPS везде; безопасные cookies `HttpOnly`, `Secure`, подходящий `SameSite`; защита CSRF там, где применима.
- Короткоживущий access session и контролируемая ротация refresh tokens; logout/revoke сессий; уведомление о важных изменениях.
- Email verification и одноразовые, ограниченного срока reset tokens; хранить хэш токена, отзывать после использования.

## 3. Роли и tenant isolation

Минимальные роли: `workspace_owner`, `workspace_admin`, `developer`, `billing_viewer`, `platform_support`, `platform_admin`. Финальные права определить матрицей. По умолчанию deny; каждый запрос проверяет принадлежность объекта workspace. Нельзя полагаться только на скрытие элементов интерфейса.

Support не получает автоматический доступ к содержимому запросов. Временный повышенный доступ — только по основанию, на ограниченное время и с audit event.

## 4. API-ключи

- Криптографически случайный высокоэнтропийный секрет; показывать полностью только один раз.
- В БД хранить безопасный hash для проверки и короткий prefix для поиска/отображения, не полный ключ.
- Привязка к workspace и project, scopes, лимиты, дата истечения (если применимо), revoke status и last-used.
- Возможность отзыва и ротации; старый ключ отзывается сразу либо после явно заданного короткого overlap.
- Передавать через `Authorization` header, никогда не query string. Не включать в analytics, логи, trace, error report или URL.
- Rate limit/quotas по ключу, проекту и workspace; защита от brute force.

## 5. Secrets и credentials поставщиков

Использовать secret manager или зашифрованное хранилище с контролем доступа. Приложение получает только необходимый secret reference. Не показывать секрет после создания, не возвращать его API кабинета, исключить из backup/export где это возможно. Ротация, отзыв, аудит чтения/изменения и план при компрометации обязательны.

## 6. Данные запросов

По умолчанию usage хранит метаданные (tenant/project, model, timestamps, duration, token counts/source, status, cost state), а не raw prompt/response. Если содержание нужно для функции чата или отладки — отдельная opt-in политика: цель, срок, доступ, удаление, экспорт и предупреждение пользователю. Не считать размещение inference в собственном ЦОД автоматическим доказательством выполнения всех юридических требований.

Определить до публичного запуска: классификацию персональных/конфиденциальных данных, сроки хранения, процедуру удаления, резервные копии, обработчиков данных и трансграничные потоки при включении внешних провайдеров. Получить профильную юридическую оценку.

## 7. Безопасность веб-приложения и операций

- OWASP-практики, CSP, безопасные заголовки, CORS allowlist, input/output limits, защита от SSRF и инъекций.
- Браузерный frontend не обращается к localhost и не получает provider credentials.
- Админка отделена логически, MFA, ограниченные сессии и аудит действий.
- Audit logs append-only/защищены от обычного редактирования; время синхронизировано.
- Регулярные обновления, dependency scanning, secret scanning, backup restore test, incident response и vulnerability reporting канал.
- Не записывать полный prompt по умолчанию; редактировать секреты и чувствительные поля в технических логах.

## 8. Инцидент компрометации ключа

1. Отозвать ключ/credential и остановить подозрительный трафик.
2. Сохранить безопасные audit/usage данные и определить затронутые проекты.
3. Уведомить клиента по утверждённой процедуре, не раскрывая секреты.
4. Проверить возможные начисления и выполнить сверку.
5. Ротировать связанные secrets, устранить причину, опубликовать postmortem при необходимости.
