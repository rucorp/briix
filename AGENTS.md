# AGENTS.md — правила работы агентов в репозитории BRIIX

Канон продукта — `docs/BRIIX.md`. Этот файл — про **процесс работы**, а не про продукт.
Задание всегда приходит в GitHub issue. Этот файл действует для каждого задания без исключений.

---

## Правило 1. Всегда работать со свежего `main` — обязательно

Агенты работают в параллельных сессиях, и твоя ветка может отстать от `main` на чужие правки.
Начинать правку на устаревшей базе — значит потерять чужое и переписать его, а это ровно тот
случай, который уже стоил времени (правки агента arena жили в старой структуре `site/`,
после переноса сайта в корень).

**Перед первой правкой в каждой задаче:**

```bash
git fetch origin
git checkout <твоя ветка сессии>
git merge origin/main
git log --oneline -3
```

**Проверочный гейт — если хоть одно условие не выполнено, стоп и не начинай правку:**

```bash
git merge-base --is-ancestor origin/main HEAD && echo "OK: main внутри" || echo "СТОП: main не свежий"
```

После слияния обязательно проверь, что критичные вещи на месте, а не только что merge прошёл:

```bash
node --check assets/js/landing.js && node --check assets/js/theme.js
grep -c '\[hidden\]' assets/css/main.css     # хотфикс модалки, должно быть не 0
grep -c '^\[data-theme' assets/css/main.css  # тёмная тема из задачи A
```

Если `main` содержит ещё и английскую версию — проверь и её:

```bash
ls en/index.html en/presentation.html
```

> Последние опорные коммиты: `7d8251b` — английская версия и i18n, `d38efa2` — фикс `[hidden]`.
> Но ориентируйся на `origin/main`, а не на этот список — он устаревает.

**Правило действует в каждом задании.** Даже если кажется, что твоя ветка свежая.

## Правило 2. Ветка

- Работай в **ветке своей сессии**. Новую ветку не создавай — сессия закреплена за одной веткой.
- **Не сливай в `main` и не пушь в `main`.** Интеграцию делает координатор после проверки.
- Коммиты делай в свою ветку, сообщения — на русском или английском, как принято в проекте.

## Правило 3. Отчёт — файлом, не комментарием

У интеграционного токена нет `issues:write`, комментарий в issue вернёт HTTP 403.
Канал односторонний: **задание — issue, отчёт — файл в `audits/`**.

- Имя отчёта: `audits/task-<N>-<короткое-имя>.md`
- В отчёте обязательно: что сделано, список файлов, **что осталось непроверенным**
- Коммить отчёт в ту же ветку

Честно пиши про непроверенное. «Проверено статически, в браузере не открывал» — полезный факт.
Отчёт, в котором нет непроверенного, обычно означает, что не всё проверено.

## Правило 4. Границы задачи

- Делай **только то, что в задании**. Ничего сверх.
- Файлы, которые можно трогать, перечислены в задании. Список — рамка, а не рекомендация.
- Не рефактори соседнее, не переименовывай классы «по пути», не поправляй «мелочи».

## Правило 5. Святое — не трогать без отдельной команды

- **Токены цветов в `assets/css/main.css`.** Вне блоков `:root` / `[data-theme]` / `@media print`
  цветов быть не должно: 0 жёстко зашитых значений. Если в твоей правке появился цвет —
  это регресс, тёмная тема и печать ломаются.
- **Правило `[hidden] { display: none !important; }`** в начале CSS. Убирать нельзя:
  авторский `display` перебивает браузерное `[hidden]`, и скрываемые блоки залипают.
  У элемента, которым управляет `element.hidden = true`, не должно быть `display` в стилях.
- **`--container: 1160px`** — константа дизайн-системы, из неё считается вся вёрстка.
- **`docs/`** — канон продукта. Только читай.

## Правило 6. Сайт

- Статик без сборки. **Никаких** npm, бандлеров, фреймворков, внешних CDN.
- Шрифты self-hosted, кириллические подмножества не выбрасывать.
- Восемь страниц: `index.html`, `presentation.html`, `investors/`, `fin-model/`
  и их зеркала в `en/`. Правки визуала обычно надо дублировать в обе версии —
  если задание не сказало иначе, спроси в issue.

## Проверка перед сдачей

```bash
node --check assets/js/*.js                 # синтаксис
grep -c '\[hidden\]' assets/css/main.css    # не 0
python3 -c "s=open('assets/css/main.css').read(); print(s.count('{'), s.count('}'))"  # скобки сходятся
```

Если правил HTML или CSS — прогони проверку локальных ссылок по изменённым страницам,
как в задаче B: битых быть не должно.

## Правило 7. Проверяй все три маркера конфликта, а не один

Мердж без разрешения конфликтов, или разрешение «на глаз», оставляет в файле осиротевшие
`>>>>>>>` — без парного `<<<<<<<`. Такой стили не является комментарием и не является
объявлением: парсер CSS съедает всё до следующей `{`, то есть **одна такая строка убивает
целое правило вместе с его содержимым**. Проверка только на `<<<<<<<` это не ловит.

Перед тем как отчитаться о слиянии:

```bash
grep -nE '^(<{7}|={7}|>{7})' assets/css/main.css assets/js/*.js
```

Пустой вывод — единственный допустимый ответ. Если вывод есть, правку не сдавать.

Раз сломанное правило не видно глазами, проверь и то, что оно вообще оживает:

```bash
grep -c '\.btn {' assets/css/main.css        # базовые кнопки
grep -c '@media print {' assets/css/main.css  # печать и PDF презентации
```

> Реальный случай 15.10.2026: в `main` уехало 8 таких строк, из-за чего на живом сайте
> были мертвы стили кнопок и весь блок `@media print` — то есть **печать презентации
> в PDF для инвестора не работала**. Нашёл агент arena при проверке задачи C.
